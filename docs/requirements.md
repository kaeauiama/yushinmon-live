## 1. 登場人物

| 役割 | 説明 | 端末 |
|---|---|---|
| 視聴者 | 主に選手の保護者。デジタル習熟度はまちまち | 大半がスマホ、一部 PC |
| 運営スタッフ | 当日の会場担当。**複数名おり、デジタルに疎い人を含む** | スマホ想定 |
| 管理者 | kaoya。事前準備・アカウント管理・障害対応 | PC / スマホ |

「運営スタッフはデジタルに疎い」という前提は、UI 設計上の最重要制約である。
操作が 1 手増えるごとに当日の事故確率が上がるものとして扱う。

## 2. 機能要件

### 2.2 自動切替（本プロジェクトの中核）

| ID | 要件 |
|---|---|
| REQ-121 | 管理者が配信 URL を差し替えたら、視聴者が操作しなくても新しい配信に切り替わる |
| REQ-122 | 切替は `player.loadVideoById()` で行い、**プレーヤーを作り直さない**。全画面表示と音声の状態を可能な限り維持する（HC-6） |
| REQ-123 | 状態変更は Firebase RTDB の購読（`onValue`）で受け取る。ポーリングを主経路にしない |
| REQ-124 | RTDB との接続が切れている場合、`.info/connected` を監視し、切断中はポーリング（15 秒間隔）にフォールバックする |
| REQ-125 | プレーヤーの `onStateChange` / `onError` を監視し、配信の終了・エラーを検知したら状態表示へ反映する |
| REQ-126 | 管理者が明示操作したときのみ、全視聴者のページを強制リロードできる（最終手段。通常運用では使わない） |
| REQ-127 | 差し替え後に自動再生がブラウザにブロックされた場合、プレーヤー外に「配信が再開しました」バナーを出して手動再生を促す。無言で止まらない |
| REQ-128 | 「通信が不安定です」は、**一度接続できたあとに切断が一定時間続いた場合にのみ**表示する。ページを開いた直後（接続確立前）や瞬断では表示しない。復帰したら即座に消す |

| REQ-131 | 取得できた設定を localStorage にキャッシュする |
| REQ-132 | RTDB から設定を取得できない場合、キャッシュを「最終取得 hh:mm 時点の情報です」と明示した上で表示する |

### 2.5 汎用化と設定の外出し

GitHub Pages で公開する以上、**リポジトリの内容も公開される**（GitHub Free では
Pages の公開に public リポジトリが必要）。したがって「秘密が無いこと」を前提に設計し、
併せて他団体がフォークして使える体裁にする。

| ID | 要件 |
|---|---|
| REQ-161 | 組織固有の値をソースコードに一切書かない。すべて `config.json` 1 ファイルに集約し、実行時に `fetch` する |
| REQ-162 | `config.json` は Firebase の接続設定・`staffEmail`・大会主催者名・公式サイト URL・退避時の連絡先を持つ。**それ以外の組織固有情報を置かない** |
| REQ-163 | `config.sample.json` と README を用意し、他団体がフォークする手順を書く |
| REQ-164 | 大会名・コート名などの表示文字列は RTDB から取る。HTML にハードコードしない |
| REQ-165 | 配色・ロゴは CSS 変数と `config.json` の 1 箇所で差し替えられるようにする |
| REQ-166 | 管理画面のテロップ・プログラム入力欄の近くに「この内容は誰でも閲覧できます」を常時表示する（HC-7 のガード） |

#### `config.json` の内容（これ以外を置かない）

```json
{
  "firebase": {
    "apiKey": "...",
    "authDomain": "<project>.firebaseapp.com",
    "databaseURL": "https://<project>.firebaseio.com",
    "projectId": "<project>",
    "appId": "..."
  },
  "staffEmail": "staff@example.invalid",
  "siteTitle": "空手道勇心門 ライブ配信",
  "officialSiteUrl": "https://example.com/",
  "fallbackContact": "お問い合わせ先の文言"
}
```

**Firebase の接続設定は秘密情報ではない**（どの Firebase プロジェクトに接続するかを示す
公開識別子であり、クライアントが知らなければ接続できない）。ただし公開されている以上、
書き込み権限は `apiKey` の秘匿ではなくセキュリティルールで守る（HC-8）。

**`staffEmail` を RTDB 側に移す案は採らない。** `config.json` はどのみち `projectId` を
含んで組織固有になるため汎用性は上がらず、一方でログイン前に RTDB 読み取りが必要になり、
**RTDB が不調なときにログインすらできなくなる**（障害対応中に致命的）。D-013 参照。

## 4. 非目標（作らないもの）

意図的に作らない。要望が出た場合は Decision Log で個別に判断する。

- 独自のチャット・コメント機能（未成年が映る配信でのモデレーション負荷に見合わない）
- 視聴者アカウント / 視聴者ログイン
- PWA 化、ネイティブアプリ
- ページ側の合言葉・パスコード入力（HC-4）
- 配信映像への加工・合成・オーバーレイ（HC-2 / HC-3）
- 過去大会のアーカイブ一覧ページ（UNDECIDED。限定公開 URL を恒久掲載する方針矛盾があるため保留）
- 視聴者数・視聴ログの収集・分析
- 多言語対応
- YouTube Data API を使った配信の自動検出（限定公開配信は取得できないため無意味）

## 5. Hard Constraints

技術的に可能でも越えない一線。**各制約は「実装しない」だけでなく、越えようとしたら弾く
ガードと、その回帰テストを対にして担保する。**

### HC-1 秘密情報・個人情報をリポジトリに置かない

特に**個人のメールアドレスをコードに埋め込まない**。旧版は管理者の個人 Gmail を
文字列分割で難読化していたが、クライアントサイドの難読化は保護ではない。
共有スタッフアカウント用の専用アドレス（個人に紐づかないもの）だけを `config.json` に持つ。

- ガード：CI またはコミット前チェックで、個人ドメインのメールアドレス・API シークレット・
  パスワードらしき文字列を検出したら失敗させる
- ガード：`config.json` 以外のファイルにメールアドレス形式の文字列が現れたら失敗させる
- 補足：Firebase の `apiKey` 等の設定値は公開前提の識別子であり、秘密情報ではない

### HC-2 YouTube プレーヤーを覆う UI を置かない

YouTube API 利用規約はプレーヤーや広告を覆い隠すことを禁じている。加えて、
スマホの全画面表示ではネイティブプレーヤーに切り替わり、重ねた要素は消えるため
技術的にも無意味である。テロップ・お知らせはすべてプレーヤーの外側に置く。

- ガード：プレーヤーのコンテナ要素の上に `position: absolute` で子を重ねない構造にし、
  レイアウトのスナップショットテストで担保する

### HC-3 配信映像への加工をページ側で行わない

得点表示・選手名・大会ロゴ・待機画面などの映像内表示は、すべて配信元（OBS /
ハードウェアスイッチャー / 配信アプリ）の責務とする。

### HC-4 視聴者向けアクセス制限を「保護」として提供しない

静的サイトでクライアント側の合言葉判定を行っても、JS を読めば突破できる。
実装しない。アクセス制限は **YouTube の限定公開のみ**とし、中継ページの URL は
「知っている人に配る」目隠しであって保護ではないことをドキュメントに明記する。

- ガード：認証ロジックを視聴ページに一切持ち込まない。`/admin/` 以外で Firebase Auth を
  import していないことをテストで確認する

### HC-5 サーバーサイドコードを持たない

GitHub Pages で完結させる。状態は Firebase RTDB に置く。

### HC-6 `iframe` の `src` 直書き換えを行わない

REQ-122 のとおり、差し替えは必ず IFrame Player API 経由。src の書き換えは
プレーヤーを作り直し、全画面と再生状態を破壊する。

- ガード：視聴ページのコードに `iframe.src =` / `setAttribute("src"` 相当の書き換えが
  存在しないことをテストで確認する

### HC-7 RTDB に個人情報を書き込まない

RTDB の読み取りは全世界に公開されている（視聴ページが無認証で読むため、非公開にできない）。
**選手名・出場者の所属・スタッフの連絡先など、個人を特定しうる情報を RTDB に置かない。**
プログラム欄は種目名までとする（「小学3・4年 形」は可、選手名は不可）。

- ガード：管理画面のテロップ・プログラム入力欄の近くに「この内容は誰でも閲覧できます」を
  常時表示する（REQ-166）
- ガード：セキュリティルールで全フィールドに文字数上限を設ける
- 限界：技術的に個人名の入力を防ぐことはできない。**運用と表示による抑止までが限界**であり、
  そのことをマニュアルに明記する

### HC-8 Firebase の新規サインアップを無効のまま保つ

書き込みルールは `auth != null` とする。**このルールは「新規サインアップが無効である」
という前提の上でのみ成立する。**

`apiKey` は公開リポジトリから誰でも取得でき、Email/Password プロバイダは既定で
誰でもサインアップできる。サインアップが有効なままだと、第三者が自分でアカウントを
作ってテロップや配信 URL を書き換えられる。サインアップを無効化することで、
`auth != null` を満たせるアカウントが手作業で作った共有スタッフアカウント 1 つだけになる。

**本構成において、これが唯一かつ必須の防御である。**

- ガード：`node tools/check-rules.js` が、実際の Firebase プロジェクトに対して
  「無認証で書き込めないこと」「新規サインアップが無効であること」
  「配信中でないイベントを無認証で読めないこと」を確認する。
  ルールを変更したあとと、大会前日の準備で必ず実行する（`docs/operations.md` 1-A）
- 補足：サインアップの確認は「存在しないアドレス + 有効な長さのパスワード」で行う。
  設定が正しく無効ならアカウントは作られない。**設定が有効だった場合に限り 1 つ作られる**
  ので、そのときはツールの指示に従って削除する（D-023）
- 注意：Google ログイン・匿名認証など**他のプロバイダを有効化するとこの前提が壊れる**。
  プロバイダを追加する場合はセキュリティルールを同時に見直す
- 注意：**メールアドレスが公開され、許可リストも持たないため、パスワードが唯一の
  防御線になる。** ログイン状態は端末保持されスタッフの入力は前日 1 回だけなので、
  覚えやすさを捨てて長いパスフレーズにする（D-014）

## 6. スコープ外だが運用上必須の前提

これらはコードではなく運用で担保する。`docs/operations.md` に手順を書く。

- YouTube 配信を**限定公開**で作成し、**埋め込みを許可**に設定すること
- YouTube の**自動終了（auto-stop）を OFF**にし、**再利用可能なストリームキー**を使うこと
- YouTube のライブチャットを**無効化**すること
- 撮影・配信について、被写体（未成年を含む）の同意を運営側が取得していること
- Firebase Console で**新規サインアップを無効化**していること（HC-8。本構成における
  唯一かつ必須の防御）
- 共有スタッフアカウントのパスワードが十分長いパスフレーズであること（HC-8）
- リポジトリを public にしても問題ない状態を保つこと（`config.json` 以外に組織固有情報が
  無いこと。REQ-161）
