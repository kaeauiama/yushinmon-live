### D-024 — 複数コートはタブ切替。管理側でコートの追加・削除もできるようにする

- **日付**: 2026-08-23（M4）
- **決定**: 視聴側・管理側ともコートをタブで切り替える。1 コートのときはタブを出さない。
  **管理画面にコートの追加・削除も実装する。**
- **スコープについて**: マイルストーンの定義は「タブ切替」までだった。追加・削除は
  Claude の判断で足している。理由は、これが無いと 2 コート目を Firebase Console で
  手作りするしかなく、**機能として完結しない**ため。不要であれば外してよい。
- **保護**: コートの追加・削除は `courts` を丸ごと書き換えるため、未保存のテキスト編集を
  巻き添えにする。そこで**未保存の変更があるあいだは操作を止める**（D-020 と同じ考え方）。
  コート切替時も未保存があれば確認を挟む。
- **同時再生はしない**: スマホでの帯域・発熱・可読性のすべてで不利なため（D-004）。
- **実機確認**: コートの追加 → 管理側タブ切替 → 視聴側タブ切替 → 削除 まで実施し、
  **削除後のデータがバックアップとバイト単位で一致**することを確認した。
- **実装中に見つけた不具合**: `addCourt` / `removeCourt` で、選択するコートの切り替えを
  `await writeUpdates(...)` の**後**に代入していた。RTDB は書き込みの解決より先に
  `onValue` を発火させる（楽観的反映）ため、再描画が終わったあとに選択が変わり、
  画面に反映されなかった。**選択の切り替えを書き込みより前に移動**して解決。
- **出所**: ユーザー承認済み（D-004）+ Claude 判断（追加・削除の実装）

### D-023 — 【訂正】サインアップ無効化の確認方法が誤っていた

- **日付**: 2026-08-23
- **訂正内容**: 「新規サインアップが有効のままである」と 2 度報告したが、**誤りだった。**
  設定は最初から正しく無効化されていた。誤っていたのは `tools/check-rules.js` の
  判定方法である。
- **原因**: `accounts:signUp` の検証順序を取り違えていた。実際の順序は
  **1. 入力形式 → 2. メールアドレスの重複 → 3.「作成（登録）を許可する」の設定**。
  1 か 2 で止まる投げ方をすると、3 の設定を確かめられない。
  - 短いパスワードで投げる → 常に `WEAK_PASSWORD`（設定に関係なく NG と誤判定）
  - 既存アドレスで投げる → 常に `EMAIL_EXISTS`（同上）
- **修正**: **存在しないアドレス + 有効な長さのパスワード**で投げる。
  設定が無効なら `ADMIN_ONLY_OPERATION` が返り、アカウントは作られない。
- **受け入れた副作用**: 設定が**有効だった場合はアカウントが 1 つ作られる**。
  3 まで到達させる投げ方が他にないため。ただしそれは既に無防備な状態のときだけであり、
  作られたこと自体が検知したい事実でもある。作成された場合は `localId` を出して
  削除を促す。アドレスは `@example.invalid` で実在しない。
- **教訓**: **ガードそのものを検証していなかった。** 「NG が出た」だけで結論を出さず、
  期待どおりの状態でも OK が出ることを一度確かめるべきだった。
  今後、外部サービスの応答で判定するガードを作るときは、
  **成功する側と失敗する側の両方を実際に確認してから**運用に載せる。
- **出所**: ユーザー指摘（Console の設定画面を提示）→ Claude 調査・修正

### D-020 — 「いま」の移動は即反映、ただしプログラム編集中はロックする

- **日付**: 2026-08-23（M3）
- **決定**:
  1. プログラムの行の追加・削除・並べ替え・文字の変更は「保存」でまとめて反映する
  2. **「いま」の位置の移動（行ごとの「ここにする」と「次の種目へ進む」）は即反映**する
  3. ただし**プログラムに未保存の変更があるあいだは 2 を無効化**し、
     「先に保存してください」と表示する
- **根拠**:
  - 「いま」は当日いちばん頻繁に動かす操作なので、保存の押し忘れで反映されない
    事故を避けたい（D-005 以来の方針。状態切替・予備切替と同じ扱い）。
  - 一方で `currentProgramIndex` は配列の添字なので、**保存前の並びと保存済みの並びが
    食い違うと別の種目を指してしまう**。状態切替や予備切替と違い、
    こちらは編集中のフィールドと意味的に結合している。
  - 両立できないので、危険な組み合わせのときだけ止める。
- **実装上の工夫**: 並べ替え・削除では「いま」が指している**行オブジェクトそのもの**を
  覚えておき、移動後に `indexOf` で追従させる。添字の計算で追わない
  （旧版はこの計算が複雑化してバグの温床になっていた）。
- **出所**: Claude 提案（M3 実装時）

### D-017 — 公開読みは「配信中のイベント」だけに絞る。App Check と Cloud Functions は採用しない

- **日付**: 2026-08-23
- **決定**:
  1. `events/$eventId` の公開読みを `root.child('_activeEvent_').val() === $eventId` に限定する。
     過去の大会の限定公開 URL を無認証で列挙できないようにする。**採用**
  2. Firebase App Check は**採用しない**
  3. Cloud Functions によるサーバーサイドロジックは**採用しない**
- **根拠**: ユーザー提起「Firebase 側で何らかのロジックが組めれば、一般公開する部分と
  秘匿する部分を分けられるかもしれない」。
  - **1 を採用する理由**: 外部依存ゼロ、当日の失敗経路ゼロで、実質的な露出が確実に減る。
    現状は `events` 配下が全公開読みのため、過去大会の限定公開 URL がすべて列挙できていた。
  - **2 を採用しない理由**: App Check は「自分のドメインからのリクエストだけ RTDB を読める」
    を実現でき `curl` でのスクレイピングは止まる。しかし**ページを開いた人には結局すべて
    見える**（`videoId` は iframe に入るので DevTools で必ず見える）ため、得られるのは
    スクレイピング対策のみ。その対価として reCAPTCHA という外部依存が増え、
    **制限ネットワークで reCAPTCHA が読めないと視聴者が何も見られなくなる**。
    D-001（配信が見られ続けることが最優先）と正面から衝突する。
  - **3 を採用しない理由**: 現在は Blaze（従量課金）プランが必要で、NFR-05 と HC-5 に反する。
- **検討して却下した案**: 匿名認証で読み取りを認証必須にする。公開された `apiKey` で
  誰でも匿名ログインできるため秘匿にならず、かつ `auth != null` が誰でも成立するように
  なって HC-8 の前提を壊す。
- **原理的な限界（明記）**: **現在配信中の `videoId` は中継ページを開けば必ず見える。**
  これ以上の秘匿は静的サイトでは実現できない。アクセス制限は YouTube の限定公開設定で行う（D-007）。
- **将来の再検討条件**: RTDB に「ページに表示しない情報」を置く必要が生じた場合のみ、
  App Check を再検討する。ただし HC-7 はそもそもそれを禁じている。
- **出所**: ユーザー提起 → Claude 提案（1 のみ採用を推奨）

### D-016 — 実装中に見つかった不具合 2 件（記録のみ）

- **日付**: 2026-08-23（M1）
- **内容**: ブラウザで実際に動かして 2 件の不具合を検出し、修正して回帰テストを追加した。
  1. **`hidden` 属性が効かない**。`.placeholder` / `.banner-action` が `display: flex` を
     持つため、ブラウザ既定の `[hidden] { display: none }` を詳細度で打ち消していた。
     隠したはずの枠が場所を取り、再生中も空白の巨大な枠が表示されていた。
     → `[hidden] { display: none !important }` を追加し、CSS の存在をテストで担保。
  2. **`LivePlayer.setVideo` の競合**。`await whenApiReady()` をまたいで二重に呼ばれると、
     二度目が「差し替え」と誤認されて未再生のプレーヤーに `loadVideoById` が走り、
     自動再生がブロックされて REQ-127 のバナーが初回表示から出ていた。
     → `videoId` の記録を `await` より前に移動。
- **教訓**: どちらも静的なテストでは発見できず、**実際にブラウザで表示して初めて見えた**。
  以降のマイルストーンでも、実装完了の条件に「実機表示の確認」を含める。
- **出所**: Claude 実施（M1）

### D-014 — 防御は「新規サインアップの無効化」1 点に絞る。UID 許可リストは採用しない

- **日付**: 2026-08-23
- **決定**: セキュリティルールの書き込み条件は `auth != null` のままとする。
  **その代わり Firebase Console で新規サインアップを無効化することを必須とする。**
  UID 許可リスト（`_staffUids_`）は採用しない。→ HC-8
- **経緯**: D-013 の検討中に、当初案の `".write": "auth != null"` が公開リポジトリ前提だと
  穴になることを発見した（公開された `apiKey` で誰でもサインアップでき、`auth != null` を
  満たせてしまう）。Claude は UID 許可リストによる二重防御を提案したが、ユーザー判断で
  採用しないことになった。
- **不採用の根拠**: ユーザー FB「GitHub Pages の知識がなければ管理者ページに到達できない
  ので最低限の分離はできている（性善説）。大事なのはむしろ当日、任意のスタッフが
  管理者ページを操作できること。ログイン PASS だけ秘匿できていればよく、それ以外の
  重要情報は見られる前提で、そもそも RTDB にも載せない」。
- **技術的な補足**: 新規サインアップを無効化すれば `auth != null` を満たせるアカウントは
  手作業で作った共有スタッフアカウント 1 つだけになるため、許可リストが無くても
  ルールは成立する。許可リストは belt-and-braces であり、落としても穴は開かない。
  **穴を実際に塞いでいるのはサインアップ無効化の方であり、これは省略できない。**
- **副作用（受け入れ）**: メールアドレスが公開され許可リストも無いため、
  **パスワードが唯一の防御線になる**。ログイン状態は端末保持でスタッフの入力は前日 1 回
  だけなので、覚えやすさを捨てて長いパスフレーズにすることで強度を確保する。
  当日の操作性は落ちない。
- **副作用（受け入れ）**: 将来スタッフごとの個別アカウントに移行する場合、
  ルールの見直しが必要になる（許可リストがあれば不要だった）。
- **残るリスク**: Google ログインや匿名認証など**他のプロバイダを有効化すると前提が壊れる**。

### D-011 — 自動切替は IFrame Player API で行い、ミュート自動再生は採用しない

### D-002 — 状態の置き場所は Firebase Realtime Database

- **日付**: 2026-08-23
- **決定**: GitHub Pages は静的配信のみを担当し、状態（配信 URL・テロップ・プログラム）は
  Firebase RTDB に置く。SDK は v9+ modular に書き直す。
- **検討した代替案**:
  - Cloudflare Workers + KV：依存は軽いが認証を自作する必要があり、自作トークンの
    管理リスクが大きい
  - GitHub リポジトリへ直コミット：ブラウザに PAT を持たせる必要があり筋が悪く、
    Pages の反映遅延で当日の差し替えに使えない。**却下**
  - GAS + スプレッドシート：実装量は最小だが、GAS が遅く CORS/キャッシュの調整が必要
- **根拠**: 旧版で実運用に耐えた実績があり、認証が既製で、データ構造をそのまま持ち込める。
- **出所**: ユーザー承認済み（「Firebase RTDB 踏襲でいい」）

### D-001 — 本プロジェクトの中心的価値は「配信 URL の差し替え耐性」と定義する

- **日付**: 2026-08-23
- **決定**: 中継ページの存在理由を「固定 URL を提供し、その裏で配信 URL を差し替えられる
  ようにすること」と定義する。他の機能（プログラム表・テロップ・複数コート）は副次的とし、

- **根拠**: ユーザー FB「これまで機材トラブルによりカメラとの接続が途切れたりして、

  中継ページの価値は上がる**（OBS が使えないことは中継ページを作らない理由にならない）。
- **出所**: ユーザー要望
