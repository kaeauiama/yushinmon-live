### D-031 — イベントの新規作成・削除・情報編集を管理画面に追加する

- **日付**: 2026-10-01
- **発端**: ユーザー要望「イベントそのものを新規作成・削除などするような UI もあれば
  管理画面で完結する操作が増えてうれしい」。
- **改修前の整理**: 管理画面でできたのは**配信中のイベントの切替だけ**だった。
  新規作成・削除に加え、**大会名・開催日・お知らせの編集もできなかった**ため、
  新しい大会を始めるには Firebase Console で `events/<ID>` を手作りする必要があった。
- **決定**（REQ-152）:
  1. **新規作成** — イベント ID・大会名・開催日を入れて作る。
     第1コートを 1 つだけ、状態「配信前」で作る
  2. **大会名・開催日・お知らせの編集** — 「保存」で反映（1 とセットで必要）
  3. **削除** — 取り消せないので安全策を付ける
- **安全策**:
  - **既存 ID を上書きしない。** 書き込む直前に `get` で存在を確かめ、あれば中止する。
    入力中にも「既にあります」と表示する
  - **作成しても `_activeEvent_` は変えない。** 視聴ページの表示は勝手に切り替わらない
  - **配信中のイベントは削除用の選択肢に出さない。** 選べないので誤って消せず、
    `_activeEvent_` が迷子にならない
  - 削除前に**中身の規模（コート数・プログラム行数）を見せて**、二段階で確認する
  - 作成・削除は**折りたたみの中**に置く（当日スタッフが触る場所から外す）
- **後方互換のために守ったこと**（ユーザー指示）:
  - **データ構造を変えていない。** 新規作成も `docs/data-model.md` と同じ形で作る
  - **セキュリティルールを変更していない。** 既存の検証を満たす値しか書き込まない。
    特に `date` は `YYYY-MM-DD` が必須なので、入力欄を日付ピッカーにし、
    **空欄のときは `date` を書き込まない**（既存の値を壊さない）
  - 既存イベントに欠けている項目（`notice` など）に耐える実装はそのまま
  - イベント ID の形式は既存の ID（`2026-autumn` など）がそのまま通る範囲に決めた
  - 旧構造のデータ（`liveList`）には一切触れていない
- **引き継いだ制約（変えていない）**: 管理画面が編集するのは**常に配信中のイベント**。
  作った直後のイベントを編集するには、いったん「配信中にする」必要がある。
  状態が `before` なら視聴ページには「配信開始までお待ちください」が出るだけなので、
  実害は小さいと判断した。
- **検証**:
  - イベント ID の判定を `assets/js/event-id.js` に切り出し、単体テスト 7 件を追加（全 63 件）。
    既存 ID が通ること、RTDB のキーに使えない文字を弾くこと、
    `constructor` などを既存と誤判定しないことを含む
  - 実ブラウザで、入力欄・ボタンの配置と、ID 入力時の説明表示、
    Firebase SDK に `get` / `set` があることを確認
- **未検証**: **作成・削除の書き込みそのもの。** パスワードが本番用に変更されており、
  こちらからログインできないため（D-030 と同じ制約）。**実機での確認が必要。**
- **出所**: ユーザー要望 → Claude 提案（範囲と安全策）→ ユーザー承認済み（A+B+C）

### D-030 — 配信前・終了後は「いま」を出さない。消す操作と視聴ページへのリンクを追加

- **日付**: 2026-10-01（初の実運用を終えて）
- **発端**: ユーザー FB「本番ではイベント運営でてんやわんやになるので、配信中や終了後に
  プログラムの『いま』の位置を直すのを忘れることがある」。
  実際、運用後の RTDB は `state: "ended"` なのに `currentProgramIndex: 1` のままだった。
- **決定**:
  1. **配信前（`before`）と終了後（`ended`）は「いま」を表示しない**（REQ-106）。
     `currentProgramIndex` の値は変えない。表示側だけで判断する
  2. 管理画面に**「『いま』を消す」**を追加（REQ-150）。`currentProgramIndex` を -1 にする。
     押した時点で即反映（状態切替・「次の種目へ進む」と同じ扱い）
  3. 管理ページのヘッダーに**視聴ページへのリンク**（別タブ）を置く（REQ-151）。
     **逆向き（視聴→管理）のリンクは置かない**
- **1 で値を消さない理由**: 中断中に「いま」が消えてしまうと、復帰後に指し直す手間が増える。
  `paused` では表示を残し、`before` / `ended` でだけ隠す。値を保持するので、
  次に配信中へ戻したときは元の行がそのまま「いま」になる。
- **2 を新しい項目にしなかった理由**: 「表示するかどうか」の設定を別に持つと、
  `currentProgramIndex` と二重管理になる。既にある -1（未指定）で同じことができるので、
  データ構造は増やさず、操作だけ足した。
- **3 を一方向にした理由**: 視聴ページは URL を知っている人に配るものなので、
  そこから管理画面へ誘導する必要がない。回帰テストで逆向きのリンクが無いことも確認する。
- **検証**:
  - 判定を `assets/js/program.js` の `visibleCurrentIndex` に切り出し、単体テスト 4 件を追加
  - 実データ（`state: "ended"` かつ `currentProgramIndex: 1`）で、視聴ページから
    「いま」が消えることを実ブラウザで確認
  - 管理ページのリンクが相対指定で正しく解決されること、「『いま』を消す」が
    既存の「次の種目へ進む」と同じ処理経路に届くことを確認
- **未検証**: **「『いま』を消す」を押して RTDB に -1 が書かれるところ。**
  パスワードが本番用に変更されており、こちらからはログインできないため。
  書き込み経路は「次の種目へ進む」と同一（D-022 で確認済み）だが、**実機での確認が必要**。
- **出所**: ユーザー要望 → Claude 実装 — 中断中は「落ち着いた帯」を出し、映像が戻れば自動で消す

- **日付**: 2026-09-14
- **発端**: ユーザー質問「中断中にしたときに画面がカバーアウトされないのは仕様？」
- **確認した仕様**: プレーヤーを残すのは意図どおり（`docs/data-model.md` の `paused`）。
  同一ストリームキー運用では配信が同じ URL で復帰するため、プレーヤーが残っていれば
  **スタッフの操作なしで映像が戻る**。
- **カバーの 2 案を検討し、どちらも採らなかった**:
  - **プレーヤーに重ねる** — YouTube API 規約違反（HC-2）。しかも全画面の視聴者には見えない
  - **プレーヤーを消して案内に差し替える** — 規約上は可能だが、
    ① 「配信中にする」の押し忘れで映像が戻らない、② 全画面が解除される、
    ③ 復帰時に作り直すため iPhone で再生し直しが要る、の代償がある
- **決定**（REQ-129）:
  1. プレーヤーは残し、**すぐ上（重ねない）に帯**を出す
  2. 帯は**警告色を使わない落ち着いた見た目**。文言は「ただいま配信を一時中断しています。
     再開まで、このままお待ちください。」
  3. **理由は決めつけない**。従来の固定文言「機材トラブルのため復旧作業中です」と、
     中断中にテロップを赤くする表示を廃止。理由はスタッフがテロップに書く
  4. **帯は「中断中にする」＋「実際に映像が止まっている」の両方がそろったときだけ出す。
     映像が戻れば、スタッフの操作を待たずに消える**
  5. 再生状態の揺れでちらつかないよう、帯の表示・非表示には各 3 秒の猶予を置く。
     ただしスタッフの操作（中断中にする／配信中にする）には即座に従う
- **根拠**: ユーザー要望「機材トラブルとは限らないので理由はテロップで」「どぎつい表示ではなく」
  「復旧したのにスタッフの操作が遅れて中断中と勘違いされるのもよくない。塩梅を考えて」。
  4 はこの最後の要望への答えで、プレーヤーが報告する再生状態を使って実現した。
  配信は数十秒遅れるため、スタッフが中断中にした時点で視聴者側はまだ映像が流れていることが多いが、
  その間は帯を出さず、手元の映像が尽きて止まった時点で出る。視聴者の実感と一致する。
- **原理的な限界（明記）**: 全画面の視聴者には、帯もテロップも見えない。
  全画面の人にも伝えたい場合は、**映像に「しばらくお待ちください」の紙を映す**（HC-3。運用マニュアルに追記）。
- **実装**: 判定を `assets/js/paused-notice.js` の `PausedNotice` に分離。
  `LivePlayer` に「実際に映像が流れているか」を知らせる `onPlaybackChange` を追加
  （既存の `onPlaying` は読み込み中も含むため、区別が必要だった）。
- **検証**:
  - 単体テスト 11 件（`tests/paused-notice.test.js`）。遅延による「手元の映像が尽きてから出る」、
    「中断中のまま映像が戻ったら消える」、「再描画で待機がリセットされない」などを含む
  - HC-2 のガードを強化し、プレーヤーの入れ物の中身が差し込み要素 1 つだけであることと、
    帯がその外側（上）にあることをテストで確認
  - 実ブラウザ（本番データに書き込まない隔離環境）で、中断中に帯がプレーヤーの上に
    重ならずに出ること、テロップが通常色のままであること、「機材トラブル」の文言が
    画面に無いこと、配信中は帯が出ないことを確認
  - 実プレーヤーからの「映像が止まっている」通知が帯の判定に届くことを確認
- **未検証**: **「映像が戻ったら帯が消える」側は実ブラウザで再現できていない。**
  検証環境では自動再生制限により、`playVideo()` を呼んでもプレーヤーが未開始のままで
  「映像が流れている」状態を作れなかったため。単体テストでは担保しているが、
  **実機での確認が必要**。
- **出所**: ユーザー要望 → Claude 提案（再生状態を条件にする方式）

### D-028 — 「通信が不安定です」を開いた直後に出さない

- **日付**: 2026-09-14
- **不具合**: 回線が正常でも、ページを開いた瞬間に「通信が不安定です」が表示されていた。
  ユーザーが実運用で発見。
- **原因**: Firebase の `.info/connected` は、**ページを開いた直後にまず `false` を返し、
  WebSocket がつながってから `true` になる**。`view.js` がこの生の値をそのまま表示に
  使っていたため、接続確立までのあいだ警告が出ていた。
  実測で、修正前は開いて 21ms で表示され、接続確立の 562ms まで出続けた
  （モバイル回線ではこの時間がさらに長くなる）。
- **決定**（REQ-128）: 表示の判定を `assets/js/connection.js` の `ConnectionWatcher` に分離し、
  次の規則にする。
  1. **一度もつながっていないうちの `false` は無視する**
  2. つながったあとに切れても、**切断が 5 秒続いたときだけ**警告する（瞬断でちらつかせない）
  3. 復帰したら即座に消す
- **表示の方針**: ユーザー要望「接続中でもなく、何も表示しないのがよい」に従い、
  起動時は「接続中…」のような表示も出さない。
- **起動時に本当につながらない場合の扱い**: 規則 1 で警告は出なくなるが、
  既存の仕組みが受け持つので沈黙の失敗にはならない。
  6 秒データが来なければ「最新の情報を取得できませんでした（キャッシュ表示）」、
  キャッシュも無ければ「配信情報を取得できませんでした」（REQ-132 / REQ-133）。
  WebSocket だけが遮断される環境では 20 秒後に REST ポーリングへ移り（REQ-124）、
  データは表示される。この場合は警告を出さないが、**表示内容は正しく、
  更新が最大 15 秒遅れるだけ**なので、誤警報より望ましいと判断した。
- **検証**:
  - 回帰テスト 8 件（`tests/connection.test.js`）。偽のタイマーで時間を進めて判定を確認
  - 実ブラウザで、**修正前のコードを同じ計測にかけて表示が出ることを確かめたうえで**、
    修正後は 3 回とも 8 秒間一度も表示されないことを確認（D-023 の教訓：計測自体が
    表示を拾えることを先に確かめる）
  - `goOffline` で回線断を模擬し、切断 2 秒では非表示・6 秒で表示・復帰で即非表示・
    1.5 秒の瞬断では非表示、を確認
- **出所**: ユーザー指摘 → Claude 修正

### D-027 — 配信機材はスマホ + RTMP アプリ。複数台を同一ストリームキーで交代させる

- **日付**: 2026-08-24
- **決定**（U-01 の解決）:
  - **RTMP 直送信アプリ**（Larix Broadcaster など）を使う。YouTube 純正アプリは使わない
    （再接続が弱い / ストリームキーを固定できない / 登録者 50 人要件がある）
  - **音声は内蔵マイク**。外部マイクは USB-C が給電と競合し、当日の失敗経路が増えるため採らない
  - **複数台を同一ストリームキーで交代**させる。目安 2 時間ごと
  - **配信中の端末は電源につながない**。待機側で充電する
  - 記録用のローカル録画は**配信とは別の端末**で行う
  - 推奨は **720p30 / 2000kbps**（6 時間で約 5.5GB）
- **根拠**: 公式予算がほぼ無い（YoloBox は個人負担になる）。一方スマホなら費用ゼロで、
  **内蔵カメラのため「カメラ抜き差しで配信が落ちる」問題（D-001 の原因）が構造的に起きない**。
- **6 時間連続で最大のリスクは発熱**。給電しながら配信すると充電回路が第二の熱源になるが、
  **2 台交代にすれば充電発熱と配信発熱が同じ端末で同時に起きない**。構造として解ける。
  この交代は「auto-stop OFF + 再利用可能なストリームキー」の上で成立し、
  **配信 URL も中継ページの URL も変わらない**。
- **採用しなかったもの**:
  - **ペルチェ式スマホクーラー** — 冷却力は高いが、筐体に固定するため
    **ファンの振動が内蔵マイクへ固体伝搬する**。内蔵マイク運用と両立しない。
    送風したい場合は大口径ファンを 30〜50cm 離して当てる
  - **パススルー（バイパス）充電** — 充電 IC のハードウェア対応が要る機種依存機能で、
    Android の開発者オプションには相当する設定が無い。`adb shell dumpsys battery set` は
    フレームワーク上の見せかけを変えるだけで電流は止まらない。sysfs を叩くには root が
    必要で、大会配信のために負う risk に見合わない。**2 台交代で不要になる**
- **信頼性を上げるオプション（前提にはしない）**: 貼り付け型ヒートシンク（無音）、
  給電が要る場合の 5W 低出力アダプタ、充電上限 80〜85%、ストレージ空き 20% 以上。
  なおストレージの空きは**発熱には無関係**で、長時間の書き込み性能低下による
  ハング・クラッシュを避けるための対策である。
- **未実施**: 会場での 1 時間テスト配信。**交代間隔・上り速度・通信量はこの実測で確定する**。
- **出所**: ユーザー判断（構成の決定）+ Claude 提案（交代方式・不採用理由の整理）

### D-026 — 本番 URL で公開し、通しで確認した

- **日付**: 2026-08-23
- **公開先**: `https://kaeauiama.github.io/yushinmon-live/`（**これが保護者に配る固定 URL**）。

### D-023 — 【訂正】サインアップ無効化の確認方法が誤っていた

### D-020 — 「いま」の移動は即反映、ただしプログラム編集中はロックする

- **日付**: 2026-08-23（M3）
- **決定**:
  1. プログラムの行の追加・削除・並べ替え・文字の変更は「保存」でまとめて反映する
  2. **「いま」の位置の移動（行ごとの「ここにする」と「次の種目へ進む」）は即反映**する
  3. ただし**プログラムに未保存の変更があるあいだは 2 を無効化**し、
     「先に保存してください」と表示する
- **根拠**:
  - 「いま」は当日いちばん頻繁に動かす操作なので、保存の押し忘れで反映されない

    食い違うと別の種目を指してしまう**。状態切替や予備切替と違い、
    こちらは編集中のフィールドと意味的に結合している。
  - 両立できないので、危険な組み合わせのときだけ止める。
- **実装上の工夫**: 並べ替え・削除では「いま」が指している**行オブジェクトそのもの**を
  覚えておき、移動後に `indexOf` で追従させる。添字の計算で追わない

- **決定**: 配信機材（OBS / ハードウェアスイッチャー / スマホ RTMP アプリ）の構成を
  UNDECIDED として保留する。ただし、**機材構成によらず有効な YouTube 側設定
  （自動終了 OFF・再利用可能ストリームキー・通常遅延）は最優先で実施する**。
- **根拠**: ユーザー FB「公式予算はほぼ無い。個人で YoloBox を買うか、撮影用スマホで
  代替するかを検討中」。機材はページ設計に影響しないため、M0 の完了を妨げない。
- **Claude の推奨（未承認）**: まず撮影用スマホ + RTMP 配信アプリ（固定ストリームキーへ
  送れるもの）を試す。費用ゼロで URL 維持の効果が得られ、内蔵カメラのため
  「カメラ抜き差しで配信が落ちる」問題自体が発生しない。YoloBox は HDMI カメラや
  複数カメラ切替が必要になった時点で検討する。
- **出所**: ユーザー要望（保留の指示）+ Claude 提案（推奨部分は未承認）

### D-011 — 自動切替は IFrame Player API で行い、ミュート自動再生は採用しない

- **日付**: 2026-08-23
- **決定**: 配信 URL の差し替えは `player.loadVideoById()` で行う。`iframe` の `src`
  書き換えは禁止（HC-6）。初回再生はユーザー操作に委ね、**ミュート自動再生は実装しない**。
- **根拠**: ユーザー要望「ユーザが画面を最大化して視聴している場合、配信が切れると
  混乱する。URL を差し替えたら自動で切り替わる仕組みを担保したい」。
  加えてユーザー懸念「ミュート自動再生はユーザがミュートに気づかないことがリスク」。
  同一プレーヤーインスタンスで `loadVideoById` を呼ぶ場合、ユーザーが既に再生操作を
  済ませていれば自動再生制限が適用されず**音声つきで継続再生される**ため、
  ミュート自動再生を使わずとも自動切替が成立する。両方の要求を同時に満たせる。
- **留保**: iOS Safari の全画面（ネイティブプレーヤー移行）時の挙動は未検証（U-02）。
- **出所**: ユーザー要望 + Claude 提案（承認済み）

### D-009 — 障害時のフォールバックは localStorage キャッシュとする

- **日付**: 2026-08-23
- **決定**: 静的な `fallback.json` に当日の配信 URL を持たせる案を破棄し、
  取得成功した設定を localStorage にキャッシュして退避表示に使う（REQ-131〜133）。
- **根拠**: ユーザー FB「限定公開なら（静的フォールバックは）役に立たないかも？」。
  指摘のとおり、当日の配信 URL は当日まで確定しないためリポジトリに置けない。
  localStorage キャッシュなら当日取得済みの URL を退避に使える。
- **出所**: ユーザー指摘 → Claude 修正提案（承認済み）

### D-008 — 管理認証は共有スタッフアカウント方式

- **日付**: 2026-08-23
- **決定**: Firebase Auth のメール/パスワードを使い、**個人に紐づかない共有スタッフ
  アカウント**を用意する。そのメールアドレスはコードに**平文で**埋め込み、スタッフは
  パスワードのみ入力する。ログイン状態は端末に保持する。
- **根拠**: ユーザー FB「当日複数のスタッフ（デジタルに疎い人も含む）でアクセスする
  可能性がある」。Google ログイン + UID 許可リスト方式は事前登録が必要で、
  登録漏れがあると当日操作できなくなる事故リスクが高い。想定被害（テロップの
  書き換え程度）に対して過剰。旧版の問題は「個人 Gmail を難読化して埋め込んでいた」
  ことであり、専用アドレスにすれば難読化自体が不要になる。
- **条件**: 個人のメールアドレスは使わない（HC-1）。パスワードは長いパスフレーズとし、
  漏洩時・スタッフ入替時に変更する。
- **出所**: Claude 提案 → ユーザー承認済み

### D-002 — 状態の置き場所は Firebase Realtime Database

- **日付**: 2026-08-23
- **決定**: GitHub Pages は静的配信のみを担当し、状態（配信 URL・テロップ・プログラム）は
  Firebase RTDB に置く。SDK は v9+ modular に書き直す。
- **検討した代替案**:
  - Cloudflare Workers + KV：依存は軽いが認証を自作する必要があり、自作トークンの
    管理リスクが大きい
  - GitHub リポジトリへ直コミット：ブラウザに PAT を持たせる必要があり筋が悪く、
    Pages の反映遅延で当日の差し替えに使えない。**却下**
  - GAS + スプレッドシート：実装量は最小だが、GAS が遅く CORS/キャッシュの調整が必要
- **根拠**: 旧版で実運用に耐えた実績があり、認証が既製で、データ構造をそのまま持ち込める。
- **出所**: ユーザー承認済み（「Firebase RTDB 踏襲でいい」）

### D-001 — 本プロジェクトの中心的価値は「配信 URL の差し替え耐性」と定義する

- **日付**: 2026-08-23
- **決定**: 中継ページの存在理由を「固定 URL を提供し、その裏で配信 URL を差し替えられる
  ようにすること」と定義する。他の機能（プログラム表・テロップ・複数コート）は副次的とし、
  中心的価値と衝突する場合は中心的価値を優先する。
- **根拠**: ユーザー FB「これまで機材トラブルによりカメラとの接続が途切れたりして、
  『繋ぎ変えても YouTube ライブに映像が復帰せず』やむなくライブを取り直すことが
  しばしば発生した。その問題を軽減するための中継ページ」。
  なお、この事情は機材構成が改善されない限り続くため、**配信機材の制約が強いほど
  中継ページの価値は上がる**（OBS が使えないことは中継ページを作らない理由にならない）。
- **出所**: ユーザー要望
